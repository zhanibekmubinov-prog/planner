# Planner — контекст проекта для Claude-сессий

**Читать первым в любой сессии.** Затем `HANDOFF.md` (что делать сейчас), затем последние записи `LOG.md`.

## Что это
**CIS Planner** — планнер-таскборд Jack'а (Zhanibek) и его команды (с v0.3 многопользовательский, с v0.6 — совместный доступ). Направления развития → проекты → задачи → делегирование людям → вспомогательные тулы (таблицы/боты) → позже агенты контроля и напоминаний.

Репо: `zhanibekmubinov-prog/planner`. Локально: `C:\Users\ZhanibekMubinov\Desktop\planner`.

## Архитектура
- Монорепо: `backend/` (FastAPI + SQLAlchemy 2 + Alembic + Postgres), `frontend/` (React 18 + Vite + TS, PWA), `agents/` (пусто, шаг 4+), `claude/` (эти заметки).
- Фронт ↔ бэк только через REST `/api/*`. Мобильное приложение позже станет вторым клиентом того же API.
- Railway, один проект, три сервиса: `postgres`, `backend` (Dockerfile, root `backend`), `frontend` (Nixpacks, root `frontend`, `serve -s dist`).
- Авторизация (v0.3): вход через Microsoft Entra (OIDC), сессия — JWT в `Authorization: Bearer`. Служебный `X-API-Token` остаётся для Swagger/скриптов и действует от имени владельца (`OWNER_EMAIL`). Видимость (v0.6, `scope.py`): своё + порученное мне + то, чем со мной поделились (`shares`); у каждой сущности в ответе поле `access`: owner | edit | view | via | assignee.
- Миграции применяются при старте бэкенда (`alembic upgrade head` в Dockerfile CMD).

## Модель данных (решения владельца, 2026-09-02; проекты и доступ — 2026-09-03)
- **Проекты (v0.6):** `Project` (direction_id, name, goal, description, color — пусто = цвет направления, status как у направления, owner_id). `Task.project_id` nullable (SET NULL): задача может лежать в проекте или прямо в направлении («Без проекта»). Проект всегда тянет своё направление в `task.directions`. Удаление проекта → задачи остаются в направлении; удаление направления → проекты удаляются каскадом.
- **Совместный доступ (v0.6):** `Share` (entity_type direction|project|task, entity_id, user_id, permission view|edit, granted_by; уникально по тройке). Направление → его проекты и задачи; проект → его задачи. `edit` — менять и добавлять; удалять и управлять доступом — только владелец. Приглашение по почте домена `ALLOWED_EMAIL_DOMAINS`: если человек не входил — создаётся заготовка `User` без `ms_oid`, при первом входе она связывается по e-mail. Задача/проект, созданные редактором внутри чужого направления, принадлежат хозяину направления (доска остаётся его). Исполнитель (`assignee`) меняет статус и пишет отчёт даже в контейнере, открытом ему только на просмотр.
- Task ↔ Direction — many-to-many (`task_directions`): задачи кросс-направленческие.
- Tool ↔ Task и Tool ↔ Direction — many-to-many (`tool_tasks`, `tool_directions`).
- `Tool.type` enum: `google_sheet | excel_sharepoint | telegram_bot | notion | other`; `Tool.source_ref` JSON (`spreadsheet_id`, `drive_id`/`item_id`, `bot_username`) — точка входа для агентов.
- `Reminder` — отдельная таблица, несколько на задачу; `channels` JSON из `telegram | email | outlook_calendar`.
- `Task.outlook_event_id` — чтобы обновлять событие в Outlook, а не дублировать.
- `MindMap` — title, `direction_id` (SET NULL), `task_id` (CASCADE), `data` JSON-дерево узлов.
- **Чеклист (v0.7):** `Task.checklist` — JSON-список `{id, text, done}` прямо в задаче (без отдельной таблицы); описание задачи остаётся свободным текстом рядом. Правится тем же `PUT /tasks/{id}`; через MCP — `add_checklist_items` / `check_item`.
- `ActivityLog` пишется на create и смену статуса — сырьё для health-score направлений.
- Люди: `Person` (имя, telegram_chat_id, email, `user_id` — связь с аккаунтом); `Delegation` (task, person, check_at, status, `report` исполнителя, `notified_at`, `assigned_notified_at`). `User` (email, name, ms_oid, is_admin, telegram_chat_id, digest_enabled). `owner_id` у Direction/Task/Tool/MindMap.

## Решения по UI (владелец, 2026-09-03)
- Референс — **Huly**: тёмная левая панель направлений, канбан по статусам, карточка задачи открывается в правой панели. Плотный рабочий инструмент, не «личный дневник».
- Основной экран — ноутбук/монитор; телефон — упрощённая адаптивная версия того же UI (PWA).
- Оформление (выбор владельца из трёх вариантов): **«Инженерный журнал»** — тёплая бумага `#f3efe6`, ржаво-красный акцент `#9a3b1c`, направления и заголовки серифом Source Serif 4, текст **Rubik**, даты/номера Source Code Pro. Шрифты только через `@fontsource` (без Google Fonts). Цвет направления — сквозной элемент: свотч, рейка на карточке, чипы, шкала прогресса в панели.
- Стартовый экран — **Карта направлений**: все направления, статистика задач, шкала внимания (владелец: «чтобы я видел, какое направление как начальник упускаю»). Сериф на названиях задач тоже.
- **Никаких системных окон браузера** (`prompt`/`confirm`/`alert`) — только свои элементы внутри страницы (`confirm.tsx`, inline-формы).
- Сайдбар (v0.4): разделы наверху одним блоком (Карта, Мне поручено, Общие, Все задачи, Майндмапы, Люди, Тулы), направления — раскрывающимся списком с фильтром; на направлении работает правая кнопка мыши (мини-меню: карта проектов, все задачи, новый проект, майндмапы, переименовать, изменить, поделиться, пауза, архив, удалить). Страницы списков — колонка по центру экрана (≤1080px), не на всю ширину.
- **Проекты в UI (v0.6, по предложению коллеги):** клик по направлению → **карта проектов** (карточки проектов со статистикой и шкалой внимания + блок «Без проекта»); клик по проекту → канбан проекта; в сайдбаре у направления стрелка раскрывает список проектов (состояние в `localStorage['planner.dirs.expanded']`), внизу списка «+ проект». Правая кнопка / «⋯» на проекте — меню (открыть, переименовать, изменить, поделиться, пауза, архив, удалить). В карточке задачи — поле «Проект»; выбор проекта сам добавляет его направление. Шапка доски — крошки «Направление › Проект».
- **Общий доступ в UI (v0.6):** «Поделиться…» в меню направления/проекта и кнопка ⇄ в шапке задачи → окно `ShareModal` (почта с подсказками из `/shares/people`, право Смотреть/Редактировать, список и отзыв). Раздел «Общие» — что открыли мне, по людям. Открытое мне помечено ⇄ в сайдбаре и на Карте направлений; при `view` карточка задачи и доска в режиме только-просмотр (`fieldset disabled`, жёлтая шапка).
- **Фильтры статусов над доской (v0.6, выбор владельца):** вкладки с подчёркиванием (Huly/Linear): Rubik, активная — ржавая линия снизу (у «В работе» — цвет направления, «Ожидание» — янтарь, «Готово» — зелёный), счётчик моно в плашке.
- **Чеклист и перенос задач (v0.7, по предложениям Нурсултана, решения владельца 2026-09-04):** в карточке задачи под описанием — секция «Чеклист» с галочками (ввёл пункт → Enter → следующий; текст правится в строке; прогресс-бар цвета направления и `2/5`), на карточке доски — тег `2/5`. Задачи переносятся между проектами **перетаскиванием на карте проектов** (строки задач в карточках проектов и «Без проекта» — как карточки между колонками доски); из сайдбара не тянем. Референс — прежний (Huly/Linear).

## Решения v0.8 (владелец, 2026-09-04, после адверсариального ревью)
- **Корзина (soft-delete):** удаление направления/проекта/задачи — в корзину (`deleted_at`), хранится 30 дней (`trash.purge_trash` из планировщика), восстановление `POST .../{id}/restore`, раздел «Корзина» в UI, тост «Отменить» 10 с после удаления. Направление уходит в корзину со своими проектами; задачи остаются живыми (связи сохраняются для восстановления). Доступ коллег при удалении снимается и сам не возвращается. «Удалить навсегда» — только из корзины.
- **Без направления:** задачи без живых направлений видны в разделе «Без направления» (сайдбар, `GET /tasks?orphans=true`); удаление непустого направления разрешено, но подтверждается вводом названия и текстом с числами из `/impact`.
- **Архив:** раздел «Архив» (направления и проекты `status=archived`) с кнопкой «Вернуть»; «В архив» — с мягким подтверждением.
- **Перенос проекта в другое направление:** режим «перенести» (задачи теряют старое направление) или «скопировать» (остаются в обоих) — `move_mode`; при переносе владелец выбирает, кому из имевших доступ через старое направление открыть проект (`grant_access_user_ids`, список из `/projects/{id}/access-preview`). Новое направление должно быть доступно владельцу проекта на edit.
- **Люди:** справочник общий, но править/удалять — только админ; удалить человека с поручениями нельзя (409); почта — только домена `ALLOWED_EMAIL_DOMAINS`; привязка Person↔User только при входе самого человека.
- **Права редактора:** редактор не может снять с чужой задачи направления/проект владельца или перенести её в контейнер, недоступный владельцу; задача, созданная в чужом контейнере, принадлежит его владельцу; владелец контейнера всегда видит задачи в нём.
- **Секреты:** `API_TOKEN` и `SESSION_SECRET` обязательны, ≥16 символов, не `change-me*` — иначе бэкенд не стартует.
- **UI-правила безопасности:** диалог подтверждения — фокус на «Отмена», Enter не удаляет, заголовок по типу сущности; правая кнопка на карточке открывает меню именно этой карточки; автосохранение карточки задачи не теряет правки при закрытии (flush) и не откатывает набранное (счётчик ревизий); PUT задачи несёт `updated_at` — при конфликте 409 и предложение перезагрузить; обновление PWA — по кнопке, не автоматически.
- **Тесты обязательны:** `python -m pytest tests -q` (backend) и `npm test` (frontend) перед каждым коммитом; новые баги сначала фиксируются падающим тестом.

## Решения по напоминаниям (владелец, 2026-09-03)
- Планировщик живёт внутри бэкенда (фоновая задача, раз в 60 с), отдельный сервис не нужен.
- Telegram — отдельный новый бот для планнера (не CIS-боты). Email и календарь — Microsoft Graph, приложение в Azure AD с application-правами `Mail.Send`, `Calendars.ReadWrite`, ящик `MS_MAILBOX`.
- Напоминание задачи можно адресовать: мне / исполнителю / мне и исполнителю (`Reminder.recipient`, v0.4). «Пора проверить» — всегда владельцу задачи; «Вам поручено» — исполнителю один раз при поручении.
- Утренняя сводка: `DIGEST_TIME` (08:30), `DIGEST_CHANNELS` (telegram,email), `DIGEST_WEEKDAYS_ONLY`.
- Переменные бэкенда: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `MS_TENANT_ID`, `MS_CLIENT_ID`, `MS_CLIENT_SECRET`, `MS_MAILBOX`, `NOTIFY_EMAIL_TO`, `FRONTEND_URL`, `APP_TIMEZONE`, `SCHEDULER_ENABLED`, `SCHEDULER_INTERVAL_SEC`.

## Решения по многопользовательскому режиму (владелец, 2026-09-03)
- Вход — только рабочие учётки Microsoft (домен `cis.kz`). Паролей в системе нет.
- Каждый видит своё + порученное ему. Поручённая задача появляется у исполнителя в «Мне поручено»; он меняет статус и пишет отчёт, автор видит.
- Сводка по человеку — то, что Я ему поручил (не всё, что у него есть).

## Решения по MCP-коннектору (владелец, 2026-09-03)
- Планнером можно управлять через Claude (claude.ai, мобильное приложение с голосом, Claude Desktop): сводки по направлениям/задачам/людям, создание направлений и задач, поручения, сроки, напоминания.
- Вход — как в CIS Platform: каждый сотрудник подключает коннектор от своего Microsoft-аккаунта и работает от своего имени (своё + порученное ему).
- **Удаления через Claude нет** — только «выполнено», пауза/архив направления, закрытие поручения.
- «Запиши / поручи / напомни / сводка» должны сразу пониматься как команды планнеру: правило зашито в инструкции MCP-сервера, плюс памятка для Personal preferences в Claude (`docs/MCP_CONNECTOR.md`).
- Код: `backend/app/routers/mcp_oauth.py`, `routers/mcp.py`, `mcp_tools.py`; документация `docs/MCP_CONNECTOR.md`. С v0.6 — 25 инструментов: + проекты и доступ.

## Решения v0.9 (владелец, 2026-09-07)
- **Бот планнера отвечает сам** (@cisplannerbot): `/id` — показать chat id, `/start <код>` — привязать чат к учётной записи, `/stop` — отключить напоминания, `/help` — справка. Искать id через сторонние боты сотруднику больше не нужно.
- Привязка — кнопкой **«Подключить Telegram»** в профиле: ссылка `t.me/cisplannerbot?start=<код>`, человек нажимает только «Запустить», chat id сохраняется сам. Ручной ввод оставлен как запасной путь.
- Код привязки **не хранится в базе** — это HMAC от id пользователя и номера суток на `SESSION_SECRET` (живёт сутки). Поэтому миграции у v0.9 нет.
- Один чат = один человек: при привязке чат снимается у остальных пользователей и записей «Люди».
- **Тот же MCP-сервер работает и в ChatGPT** (правка параллельной сессии, 2026-09-07): в `REDIRECT_HOST_ALLOWLIST` добавлены `chatgpt.com` и `openai.com`, остальная схема OAuth без изменений — сотрудник может подключить планнер и в Claude, и в ChatGPT. Подробности — `docs/MCP_CONNECTOR.md`.
- Вебхук защищён секретом `TELEGRAM_WEBHOOK_SECRET` (заголовок `X-Telegram-Bot-Api-Secret-Token`); вебхук всегда отвечает `{"ok": true}`, ошибки только в лог.

## Решения v0.10 — внешние участники (владелец, 2026-09-07)
- Приглашать людей не из `ALLOWED_EMAIL_DOMAINS` может **только админ** — раздел «Гости» в сайдбаре виден лишь ему.
- Гость входит **не через Microsoft**, а по одноразовой ссылке на свою почту (у подрядчиков Microsoft-учётки может не быть). Пароли в системе не появляются.
- **Права гостя такие же, как у сотрудника** (решение владельца): свои направления, задачи, поручения. Контроль — список гостей и то, чем с ним поделились.
- Отзыв доступа — удаление из списка «Гости»; отдельного выключателя и срока действия не делаем. Отзыв мгновенный: проверка «гость всё ещё в списке» идёт в `auth.current_user`, поэтому перестают работать и уже открытые сессии, и лежащие в почте ссылки.
- Ограничения, заложенные в код: ссылка живёт 15 минут и срабатывает один раз (в базе только SHA-256 хеш), новый запрос гасит прежнюю; 3 запроса на адрес и на IP за 15 минут; сессия гостя 30 дней, как у сотрудника (уточнение владельца 2026-09-07: входить заново раз в неделю неудобно, а отзыв доступа мгновенный и от срока сессии не зависит); сотрудник рабочего домена этим входом воспользоваться не может (иначе это обход корпоративного входа), и рабочую почту нельзя добавить в гости.
- Ответ на запрос ссылки всегда одинаковый — иначе по нему перебором вычисляется список гостей.
- Проверки домена в «Поделиться», справочнике «Люди» и `create_person` через Claude пропускают адреса из списка гостей. Документация — `docs/GUESTS.md`.
- **Пароль гостя (уточнение владельца в тот же день):** одной почты для входа недостаточно — у гостя есть пароль. Придумывает его сам гость по ссылке из письма (владелец пароля не знает), хранится `scrypt`-хеш с солью. Обычный вход — почта + пароль; ссылка нужна только для первого входа и сброса. Сброс гость делает сам письмом (владелец выбрал удобство), поэтому добавлены две страховки: смена пароля гасит все прежние сессии гостя (номер версии пароля в сессии) и владельцу приходит уведомление о смене. Подбор ограничен: 5 попыток на адрес и на IP за 15 минут. Требования к паролю: ≥10 символов, не равен почте, не очевидный.

## Правила работы в этом проекте
- Ответы по-русски. Владелец — не разработчик: команды давать готовыми к копированию, по блокам, с ожидаемым результатом.
- Терминал владельца — **PowerShell**, не cmd: `.\.venv\Scripts\Activate.ps1`, пути абсолютные (`C:\Users\ZhanibekMubinov\...`), без `%VAR%`.
- Изменения файлов отдавать либо готовыми файлами на замену, либо одной точной правкой с указанием строки. Не давать длинные diff'ы. В Cowork-сессии с подключённой папкой файлы можно записывать прямо в репо владельца — но **git не запускать** (оставляет `index.lock`), коммитит владелец.
- Локальная проверка перед пушем: бэк — `uvicorn` + `/docs`; фронт — обязательно `npm run build` (dev не проверяет типы!).
- Модели меняем → `alembic revision --autogenerate -m "..."` → `alembic upgrade head` → миграцию коммитим.
- **Каждая сессия обязана** перед завершением: (1) добавить запись в `LOG.md`, (2) обновить `HANDOFF.md` — статус и следующий шаг. Без этого следующая сессия не знает, где мы. Это часть задачи, а не опция.
- Решения владельца (модель, приоритеты, UX) фиксировать в этом файле в разделе «Модель данных» или новом разделе «Решения».
