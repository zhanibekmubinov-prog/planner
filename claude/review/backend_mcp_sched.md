Область: `backend/app/mcp_tools.py`, `routers/mcp.py`, `routers/mcp_oauth.py`, `scheduler.py`, `notify.py`, `digest.py`, `routers/notify.py`.
Метод: чтение кода + прогон на sqlite (скрипты в (скрипты воспроизведения — вне репо), см. раздел «Подтверждено скриптом»). Файлы `/root/planner` не менялись.

## Критично

### К1. Consent-фишинг: чужой OAuth-клиент получает полный доступ к планнеру жертвы одним кликом «Разрешить»
`routers/mcp_oauth.py:92-112` (DCR без аутентификации), `:131-160` (authorize), `:180-200` (страница согласия), `:215-235` (consent POST), `routers/auth.py:116-119`.

**Воспроизведение (подтверждено):**
1. Атакующий: `POST /oauth/register {"client_name":"Claude","redirect_uris":["https://evil.example/cb"]}` → `client_id` (регистрация открыта всем, лимитов нет).
2. Атакующий: `GET /oauth/authorize?client_id=…&redirect_uri=https://evil.example/cb&code_challenge=<свой>` → 302 на `login.microsoftonline.com/...&state=mcp:<key>`. Эту ссылку он отправляет жертве («подтвердите подключение Claude»).
3. Жертва входит через Microsoft → `/api/auth/callback` записывает `pending.user_id = жертва` → `/oauth/consent?k=<key>` показывает «**Claude** просит доступ к планнеру от имени <жертва>» — домен `evil.example` на странице **не показан**, cookie-привязки к браузеру, начавшему authorize, нет.
4. Жертва жмёт «Разрешить» → 302 `https://evil.example/cb?code=…` → атакующий обменивает код на токены (`client_id` и `redirect_uri` в `/oauth/token` необязательны) → `initialize` отвечает «планнер пользователя Victim».

**Ожидалось:** авторизационный запрос привязан к браузеру инициатора; пользователь видит, куда уйдёт код.
**Исправление:** на `/oauth/authorize` ставить httpOnly-cookie с случайным значением и сохранять его хеш в `McpPendingAuth`; на `/oauth/consent` (GET и POST) требовать совпадения. На странице согласия показывать хост `redirect_uri`. Дополнительно — allow-list redirect-хостов (`claude.ai`, `claude.com`, `localhost`) в `_valid_redirect_uri`, раз клиент фактически один.

### К2. Авторизационный код можно обменять несколько раз (гонка на флаге `used`)
`routers/mcp_oauth.py:276-286`.

**Воспроизведение (подтверждено на sqlite):** один код, 4 параллельных `POST /oauth/token grant_type=authorization_code` → статусы `[200, 400, 200, 200]`, в `mcp_tokens` появилось 3 пары токенов на один код. Чтение `row.used` и запись `row.used = True` + `commit()` в `_issue_tokens` не атомарны; на Postgres без блокировки поведение то же.
**Ожидалось:** код одноразовый (RFC 6749 §4.1.2), повтор → отзыв всех токенов, выданных по этому коду.
**Исправление:** атомарный `UPDATE mcp_auth_codes SET used=true WHERE code_hash=:h AND used=false` и проверять `rowcount == 1`; либо `with_for_update()` при выборке. То же для ротации refresh-токена (`:297`).

## Высоко

### В1. Редактор задачи может привязывать её к чужим направлениям (view-only) и отрывать от направлений/проекта владельца
`mcp_tools.py:588-601` (`update_task` add/remove_directions, project=null), `:770` (`add_tool` directions).

**Воспроизведение (подтверждено):** Jack делится задачей T1 с Nur на `edit`, направление «Эмба» — только `view`. Nur вызывает `update_task(task="Подписать договор", add_directions=["Эмба"])` → `+Эмба` (REST в `scope.fetch_directions_for_task` требует `get_direction_editable` и вернул бы 403). Затем `remove_directions=["Эмба"]`, `project=null`, `add_directions=["Нурлан личное"]` → задача Jack исчезла с его доски «Эмба» и из проекта и висит в направлении Nur. `add_tool(directions=["Эмба"])` — тул вешается на view-only направление (REST: только `get_owned`).
**Ожидалось:** как в REST — добавлять только в направления с правом `edit`/owner; удалять из направления — только владелец/редактор этого направления.
**Исправление:** в `t_update_task` оборачивать `resolve_direction(...)` в `_editable(...)` для `add_directions` и `remove_directions`; в `t_add_tool` ограничить направления своими (`owner_id == user.id`), как в `routers/tools.py`.

### В2. Открытая рассылка с корпоративного ящика на любой внешний адрес («Вам поручено»)
`mcp_tools.py:516-523` (`_find_or_create_person`), `:746-758` (`create_person` без валидации email), `scheduler.py:220-241` (`process_assignments`), `notify.py:52-57`.

**Воспроизведение (подтверждено):** любой авторизованный пользователь: `create_person(name="Внешний", email="victim@gmail.com")` → `create_task(title="Оплатите счёт: http://evil.example/pay", assign_to=["Внешний"], comment="срочно, перейдите по ссылке")` → через минуту `process_assignments` отправляет через Graph с `MS_MAILBOX` письмо «CIS Planner · вам поручено: Оплатите счёт: http://evil.example/pay» на `victim@gmail.com`. Тема и тело — под контролем отправителя, домен не проверяется (в `share_access` домен проверяется через `find_or_invite_user`, здесь — нет).
**Исправление:** в `create_person`/`_find_or_create_person` проверять домен по `settings.allowed_domains` (как в `shares.find_or_invite_user`); слать «вам поручено» только людям с `user_id` (вошедшим в планнер) либо только на разрешённые домены.

### В3. `/oauth/register` — без аутентификации и лимитов
`routers/mcp_oauth.py:97-112`.
**Подтверждено:** 200 клиентов за 1.4 с, без токена. Это и основа для К1, и заполнение таблицы `mcp_clients` (записи никогда не удаляются).
**Исправление:** rate-limit по IP, TTL для клиентов без ни одной авторизации (чистить вместе с `McpPendingAuth`), allow-list redirect-хостов.

### В4. Batch JSON-RPC без ограничений — усиление ответа ×2000 и неограниченное тело
`routers/mcp.py:71-73`.
**Подтверждено:** `POST /mcp` с массивом из 2000 `tools/list` → ответ 51.9 МБ за 5.6 с одним запросом с валидным токеном. Тело 5 МБ мусора принимается и парсится (400 после полного чтения). Лимитов размера тела/числа элементов батча/частоты нет.
**Исправление:** ограничить батч (например ≤ 20) и размер тела (~64 КБ) — проверять `Content-Length` до чтения; батчи в MCP 2025-06-18 вообще убраны — можно отвечать `-32600`.

### В5. Тексты внутренних исключений уходят Claude (и пользователю) вместе с SQL и параметрами
`mcp_tools.py:1122-1127`.
**Подтверждено:** `create_task(title="descr", description=["a","b"])` → `{"error":"внутренняя ошибка сервера: ProgrammingError: (sqlite3.ProgrammingError) … [SQL: INSERT INTO tasks (title, description, …) VALUES …] [parameters: (…)]"}`. На Postgres будет полный текст SQL, имена таблиц/колонок и значения параметров.
**Исправление:** возвращать только `type(e).__name__` и короткий id инцидента; полный трейс — в лог (уже есть `_log.exception`). Приводить строковые поля (`description`, `comment`, `report`, `url`, `goal`, `note`) через `str()`/отклонять не-строки до записи.

### В6. Бот-токен Telegram печатается в лог при каждой отправке
`notify.py:17-19`; `main.py:11` (`logging.basicConfig(level=INFO)`).
**Подтверждено:** httpx на уровне INFO пишет `HTTP Request: POST https://api.telegram.org/bot123456:SECRET_BOT_TOKEN_XYZ/sendMessage "HTTP/1.1 200 OK"`. В Railway-логах токен виден всем, у кого есть доступ к проекту.
**Исправление:** `logging.getLogger("httpx").setLevel(logging.WARNING)` в `main.py`, либо передавать токен не в URL-пути (у Telegram альтернативы нет — значит, только глушить лог).

## Средне

### С1. Точное совпадение по названию побеждает даже если это выполненная задача
`mcp_tools.py:147-149`, `:200`.
**Подтверждено:** задачи «Договор» (done) и «Договор с Эмбой» (open). Голосовое «возьми в работу договор» → `set_task_status(task="договор", status="in_progress")` → изменена **выполненная** «Договор» (`выполнено → в работе`), без предупреждения. `resolve_task` ищет по всем видимым задачам, включая done.
**Ожидалось:** для write-инструментов сначала искать среди открытых; done — только при явном `include_done` или если открытых кандидатов нет, с пометкой в ответе.
**Исправление:** в `_match` для задач при неоднозначности/точном совпадении предпочитать не-done; если единственный кандидат — done, возвращать `ToolError` с hint «задача уже выполнена, id N — повторите с id».

### С2. `create_person` пропускает «Ержан» при существующем «Ержан Сапаров» → далее поручения уходят не тому
`mcp_tools.py:746-752`, `:516-523`.
**Подтверждено:** есть «Ержан Сапаров»; `create_person(name="Ержан")` → создан; после этого `delegate_task(person="Ержан")` **молча** назначает нового «Ержан» (точное совпадение), а не Сапарова. `create_person_if_missing=true` с падежом «Ержану» создаёт третьего человека «Ержану». Справочник людей общий на всех пользователей, чужие опечатки видны всем.
**Исправление:** в `create_person` считать дубликатом совпадение по первому слову/по префиксу и возвращать кандидатов; при `create_*_if_missing` — создавать только если запрос длиннее одного слова или нет частичных совпадений; нормализовать ё→е и регистр.

### С3. Ё/е и словоформы не нормализуются — «не найдено» вместо совпадения
`mcp_tools.py:146-158`.
**Подтверждено:** задача «Отчёт по ТО», запрос «отчет по то» → «не найдено». «договор эмба» (стем без окончания) — «не найдено». При этом `create_direction_if_missing`/`create_person_if_missing` после такого «не найдено» создают дубликаты.
**Исправление:** нормализовать `ё→е`, убирать пунктуацию, сравнивать по префиксам слов (≥4 символов) в fallback-поиске.

### С4. Списковые аргументы строкой «через запятую» становятся одним элементом
`mcp_tools.py:49-56`, `:531-539`.
**Подтверждено:** `create_task(directions="Снабжение, Бурение", create_direction_if_missing=true)` → создано направление **«Снабжение, Бурение»**; `add_checklist_items(items="a, b, c")` → один пункт «a, b, c»; `add_reminder(channels="telegram, email")` → ошибка. Claude в голосовом режиме регулярно шлёт такие строки.
**Исправление:** в `_list` строку с `,`/`;`/переводом строки резать на элементы; для `create_*_if_missing` запрещать создание, если в имени есть запятая.

### С5. Нецелые `limit`/`due_within_days` → «внутренняя ошибка сервера»
`mcp_tools.py:378`, `:383`.
**Подтверждено:** `list_tasks(due_within_days="неделя")` и `list_tasks(limit="все")` → `ValueError` → ответ с hint «сбой на стороне планнера, не повторяйте» — Claude прекращает попытки, хотя проблема в аргументе. `limit=-1` → пустой список при `count=1`.
**Исправление:** `parse_int(value, field, min, max)` с `ToolError` как у `parse_priority`.

### С6. Напоминание `recipient=assignees` без поручений / владелец без Telegram — 1440 записей `failed` в `activity_log` и WARNING каждую минуту сутки
`scheduler.py:99-101`, `:134-146`.
**Подтверждено:** `add_reminder(recipient="assignees")` у задачи без поручений → `results={"assignees": "…нет открытых поручений"}` → `ok=False`, `sent_at` не ставится, каждый тик новая строка `failed`; через 25 ч — `gave_up`. То же для владельца без chat id (`'у владельца задачи не указан Telegram chat id'`) — ошибка конфигурации, а не временный сбой, но ретраится сутки. Пользователь узнаёт о «непришедшем» напоминании только из логов.
**Исправление:** делить ошибки на постоянные (нет адресата/канал не настроен → сразу `sent_at`+`gave_up` и уведомление владельцу другим каналом или в `get_overview`) и временные (сеть/5xx → ретрай с backoff, а не каждую минуту); писать в `activity_log` не каждую попытку, а первую и финальную.

### С7. Дайджест при ошибке отправки повторяется каждый тик до полуночи
`scheduler.py:246-249`, `:273`, `:281-284`.
**Подтверждено:** у пользователя `telegram_chat_id` задан, бот отвечает ошибкой → `digest_due` каждый тик `True` (учитывается только `action == "sent"`), 3 тика → 3 строки `failed`; за день ~900 попыток и ~900 вызовов Telegram API на пользователя. При позднем рестарте бэкенда дайджест уйдёт и в 23:59 (`digest_time_passed` — «после времени», без окна).
**Исправление:** считать попытку `failed` тоже «сделанной сегодня» (или ограничить N ретраев с интервалом ≥ 15 мин); отправлять только в окне `[digest_time, digest_time+2h)`.

### С8. Одна «битая» запись останавливает весь тик планировщика навсегда
`scheduler.py:134-146`, `:292-300`.
**Подтверждено (инъекцией исключения в `render`):** исключение вне per-channel `try` (рендер, отсутствующая связь, ошибка БД) прерывает `process_due` → `tick` → `run_forever` ловит и через минуту повторяет с той же записью первой в очереди (`order_by fire_at`). Остальные напоминания, «пора проверить», уведомления о поручениях и дайджест не обрабатываются, пока запись не исправят руками.
**Исправление:** оборачивать обработку каждой записи в `try/except`, при ошибке писать `activity_log failed` и ставить `sent_at`/пропускать на N минут; не обрывать цикл.

### С9. Двойные отправки при двух экземплярах бэкенда (деплой Railway) — блокировок нет
`scheduler.py:126-146`, `:190-204`, `:220-241`. **Не проверено** (нельзя поднять два инстанса), но по коду: `SELECT … WHERE sent_at IS NULL` → отправка → `UPDATE`; при перекрытии старого и нового контейнера обе копии отправят одно и то же в Telegram/почту/календарь (для календаря — два события, т.к. `outlook_event_id` записывается после).
**Исправление:** `UPDATE reminders SET sent_at=now() WHERE id=:id AND sent_at IS NULL` до отправки с проверкой `rowcount`, либо `SELECT … FOR UPDATE SKIP LOCKED`; либо advisory lock на тик.

### С10. `create_person` с чужой почтой привязывает запись к чужому аккаунту
`mcp_tools.py:753-756`, `routers/auth.py:110-115`.
**Подтверждено:** Nur: `create_person(name="Хакер", email="jack@cis.kz")` → `in_planner: true`, `user_id = Jack`. Теперь при входе Jack его «человек» — «Хакер» (callback ищет Person по `user_id` первым), поручения «Хакеру» попадают в inbox Jack, имя видно всем в справочнике и в уведомлениях.
**Исправление:** не привязывать `user_id` в `create_person`; связь Person↔User создавать только в `/auth/callback` от имени самого пользователя; имя Person для вошедших брать из `User.name`.

### С11. JSON-RPC: `params`/`name` не-объект → 500 вместо ошибки протокола
`routers/mcp.py:37`, `:53`; `mcp_tools.py:1102`.
**Подтверждено:** `{"method":"tools/call","params":[1]}`, `"params":"x"`, `{"method":"initialize","params":[1]}`, `"params":{"name":["get_overview"]}` → HTTP 500 `Internal Server Error` (`AttributeError`/`TypeError: unhashable`). Трейс в лог, клиенту — не-JSON-RPC ответ; Claude покажет «сбой».
**Исправление:** `params = msg.get("params"); if not isinstance(params, dict): return _error(req_id, -32602, …)`; `name = str(params.get("name") or "")`.

### С12. `/api/notify/run-now` и `/digest` доступны любому пользователю
`routers/notify.py:55-67`.
**Подтверждено:** не-админ Nur → `POST /api/notify/run-now` → 200 и отправлено напоминание Jack (`mails sent to: ['jack@cis.kz']`) — обработка глобальная, а не «своих». `/digest` с произвольными `channels` шлёт себе; `/test` — себе. Ограничений частоты нет: цикл `/digest` = спам Telegram/Graph API и рост `activity_log` (`sent_manual`).
**Исправление:** `run-now` — `require_admin`; `/digest` и `/test` — простой rate-limit (например 1 раз в минуту на пользователя, проверка по `activity_log`).

## Низко

### Н1. Числовое название трактуется как id
`mcp_tools.py:140-145`. **Подтверждено:** задача «2026», `get_task(task="2026")` → «id 2026 не найдено». Исправление: при отсутствии id пробовать поиск по названию.

### Н2. Дубли направлений/проектов из-за пунктуации; дубли пунктов чеклиста
`mcp_tools.py:472`, `:642`. **Подтверждено:** «Снабжение.» создаётся рядом со «Снабжение»; `add_checklist_items` дважды с одним текстом → два одинаковых пункта, после чего `check_item("цены")` — «несколько совпадений». Исправление: нормализовать имя (пунктуация, пробелы) и пропускать уже существующие пункты чеклиста (вернуть `skipped`).

### Н3. `title`/`name`/`url`/`color` — любой тип, без валидации
`mcp_tools.py:580`, `:487`, `:768`, `:476`. **Подтверждено:** `create_task(title=["a","b"])` → задача `"['a', 'b']"`; `update_direction(name=123)` → «123»; `color="<script>alert(1)</script>"` сохраняется; `url=123`; `update_task(title="   ")` — отвечает `updated: ["title"]`, не меняя ничего; заголовок 1000 символов принимается в `String(300)` (на Postgres будет `DataError` → В5). Исправление: единая валидация типов/длины; color — regex `^#[0-9a-f]{6}$`.

### Н4. `share_access(email=[...])` создаёт пользователя с почтой `"['nur@cis.kz']"`
`mcp_tools.py:851`. **Подтверждено:** `with.email = "['nur@cis.kz']"`, `name = "['nur"`. Затем `allowed_domains` не сработает, т.к. домен `cis.kz']`. Исправление: `email = _list(a,"email")[:1]` + валидация формата.

### Н5. `update_delegation` расходится с REST: редактор направления не может править поручение
`mcp_tools.py:700-702` vs `routers/simple.py:87-88` (`get_task_editable`). **Подтверждено:** Nur с `edit` на направлении получает «Менять поручение может владелец задачи или сам исполнитель». Не дыра, но неконсистентность прав между UI и Claude. Исправление: использовать `task_access(...) in WRITE` вместо `owner_id == user.id`.

### Н6. Редактор направления может его архивировать и переименовать
`mcp_tools.py:483-499`. **Подтверждено:** Nur (`edit`) → `update_direction(status="archived")`, `name="Моё направление"`. Совпадает с REST (`get_direction_editable`), т.е. по дизайну, но для голосового канала ошибка распознавания названия = архив чужой доски без подтверждения. Рекомендация: `archived` и `name` — только владелец; либо требовать `id` (не название) для `status=archived`.

### Н7. Прошедшие даты принимаются молча
`mcp_tools.py:79-104`. **Подтверждено:** `add_reminder(fire_at="2020-01-01T09:00")` — создано и отправлено на следующем тике; `delegate_task(check_at="2020-…")` — «пора проверить» сразу; `deadline="2020-01-01"` — задача сразу просрочена. Claude при ошибке года (частая ошибка в голосе) спамит. Также `"2026-09-05T"` (len 11) для `deadline` проходит через `s[:10]`, а для `next_check_at` — ошибка; `"20260905"` → `2026-09-05 00:00` (не 09:00). Исправление: для `fire_at`/`check_at` в прошлом более чем на 5 мин — `ToolError` с hint «дата в прошлом, уточните»; для `deadline` в прошлом — предупреждение в ответе.

### Н8. Сравнение служебного токена не константное; токены никогда не отзываются и не чистятся; `commit()` на каждый запрос
`routers/mcp_oauth.py:309`, `:318`; отсутствие `/oauth/revoke`. **Подтверждено:** `token == settings.api_token` (в `consent_post` — `compare_digest`, здесь — нет); удаление коннектора в Claude (как написано в `MCP_CONNECTOR.md`) **не** отзывает refresh-токен на сервере — он действует 30 дней; таблица `mcp_tokens` только растёт (5 строк после одного флоу с гонкой). Исправление: `secrets.compare_digest`; RFC 7009 `/oauth/revoke`; периодическая чистка истёкших/отозванных; `last_used_at` обновлять не чаще раза в минуту.

### Н9. `_valid_redirect_uri` — префиксная проверка; `code_challenge` без проверки формата
`routers/mcp_oauth.py:92-93`, `:140`. **Подтверждено:** принимаются `http://localhost.evil.com/cb`, `http://127.0.0.1.evil.com/cb`, `https://` (пустой хост), URI с `#fragment` (RFC 6749 §3.1.2 запрещает); `code_challenge="abc"` (не 43 символа base64url) принимается. Практический эффект ограничен К1/В3, но чинить вместе: парсить `urlparse`, проверять `hostname in {"localhost","127.0.0.1"}` для http, запрещать fragment, `len(code_challenge)==43`.

## Что проверено и в порядке

- `_match` при нескольких частичных совпадениях возвращает `ToolError` с кандидатами, а не берёт первый (в т.ч. когда одноимённое чужое направление открыто на просмотр — «Снабжение» id 1 и id 3 → ошибка, не тихий выбор).
- View-only пользователь: `update_task`, `set_task_status`, `delegate_task`, `add_reminder`, `update_direction`, `update_project`, `share_access`, `revoke_access`, `add_checklist_items`, `check_item` — все отклоняются; `share_access`/`revoke_access` — только владелец (`_share_target`). Исполнитель: статус, `check_item`, `report` — как задокументировано.
- PKCE S256 считается корректно, `plain` отклоняется; ротация refresh отзывает старую пару; повтор старого refresh → 400; `state` экранируется в редиректах ошибок; pending/код имеют TTL.
- `/mcp` без токена → 401 с `WWW-Authenticate: … resource_metadata=…`; неизвестный метод → `-32601`; уведомления → 202; `arguments` строкой/`null`/массивом → `{}` → понятная `ToolError`, не 500.
- Telegram HTML: заголовки задач, комментарии, имена экранируются `html.escape` в `render`/`render_delegation`/`render_assignment`/`digest.render` (`<b>&</b>` → `&lt;b&gt;&amp;…`). Тема письма — raw, но это plain text.
- sqlite-наивные `datetime` приводятся через `_utc` как UTC — согласовано с записью (`astimezone(utc)` в `parse_dt`). DST для `Asia/Oral` отсутствует.
- `DIGEST_WEEKDAYS_ONLY` — суббота 09:00 → не отправляется.
