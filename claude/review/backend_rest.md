Дата: 2026-09-04. Область: `app/models.py`, `app/scope.py`, `app/schemas.py`, `app/crud.py`, `app/auth.py`, `app/routers/{directions,projects,tasks,shares,simple,tools,mindmaps,auth}.py`.
Метод: чтение кода + воспроизведение на sqlite (`PRAGMA foreign_keys=ON`, чтобы эмулировать `ondelete` Postgres) через `TestClient`. Скрипты: (скрипты воспроизведения — вне репо). Все находки без пометки «не проверено» воспроизведены реально.

Участники в сценариях: **Джек** — владелец, **Нурлан** — коллега с правом `edit`, **Ева** — коллега с правом `view` / исполнитель.

## Критично

### К1. `PUT /api/delegations/{id}` позволяет перенести поручение на ЛЮБУЮ задачу → чтение и смена статуса чужих задач
**Файл:** `app/routers/simple.py:86-91` (`deleg_update`), схема `DelegationIn` содержит `task_id`.
**Воспроизведение:**
1. Джек делится с Нурланом задачей A (`edit`). У Джека есть приватная задача S.
2. Нурлан: `POST /api/delegations {task_id: A, person_id: <Person Нурлана>}` → 201.
3. Нурлан: `PUT /api/delegations/{id} {task_id: S, person_id: <Person Нурлана>}` → **200**.
4. Нурлан: `GET /api/tasks/S` → **200**, `access: assignee`; `POST /api/tasks/S/status {status: done}` → **200**.
**Что происходит:** проверка `get_task_editable` делается только для *старой* `obj.task_id`, затем `setattr` перезаписывает `task_id` из тела. Нурлан становится исполнителем любой задачи по её id (id последовательные — перебор тривиален), видит заголовок/описание/чеклист, меняет статус, получает напоминания `recipient=assignees`.
**Должно быть:** `task_id` поручения неизменяем (или проверять `get_task_editable` и для нового `task_id`).
**Исправление:** в `deleg_update` исключить `task_id` из применяемых полей (`d = data.model_dump(exclude={"task_id"})`) либо при `data.task_id != obj.task_id` вызывать `get_task_editable(db, user, data.task_id)`. Аналогично для `rem_update` (см. В3).

### К2. Дефолтные секреты `SESSION_SECRET="change-me-too"` / `API_TOKEN="change-me"` → подделка JWT любого пользователя
**Файл:** `app/config.py:6,11`, `app/auth.py:17-20,49-51`.
**Воспроизведение:** без переменной `SESSION_SECRET` (в `test_v06.py` и в harness её нет) выполнить
`jwt.encode({"sub": "1", "exp": 4102444800}, "change-me-too", "HS256")` → `GET /api/auth/me` → **200, jack@cis.kz** (владелец, `is_admin`).
**Что происходит:** приложение стартует и работает с публично известным секретом; достаточно забыть переменную на Railway — и любой, кто знает URL бэкенда, входит от имени владельца (и от имени любого `user_id`). `X-API-Token` со значением `change-me` даёт то же самое.
**Должно быть:** отказ старта при отсутствии/дефолтном секрете.
**Исправление:** в `Settings` сделать `session_secret: str` и `api_token: str` обязательными (без default) либо добавить валидатор, который бросает исключение при значениях `change-me*` или длине < 32. Дополнительно (низко): в `current_user` JWT без `exp` принимается (`jwt.decode` не требует exp) — добавить `options={"require": ["exp", "sub"]}`.

## Высоко

### В1. Редактор (`edit`) может «увести» или «потерять» задачу владельца: убрать все направления/проект, перенести в своё направление или проект
**Файл:** `app/routers/tasks.py:14-28` (`_apply`), `app/scope.py:222-231` (`fetch_directions_for_task` — проверяет только *добавляемые* направления, удаление любых разрешено), `tasks.py:64-69` (`update` — коммит до повторной проверки доступа).
**Воспроизведение (три варианта, все подтверждены):**
- (a) Джек делится направлением D (`edit`). Нурлан: `PUT /api/tasks/{t} {..., direction_ids: [<своё направление N>]}` → ответ **404**, но изменение **сохранено**: у Джека `GET /tasks/{t}` → `directions: [{id: N, name: "Личное (Nur)"}]`; `GET /tasks?direction_id=D` → `[]`. Нурлан тоже теряет доступ (404).
- (b) `PUT /api/tasks/{t} {direction_ids: [], project_id: null}` → 404, но задача стала сиротой: `project_id=None, directions=[]`, пропала с доски и из проекта Джека, видна только в «Все задачи».
- (c) `PUT /api/tasks/{t} {project_id: <проект Нурлана>, direction_ids: []}` → задача Джека лежит в проекте Нурлана (`project_id=2`, `directions=[Личное (Nur)]`), Джек `GET /projects/2` → 404 — видит проект, к которому у него нет доступа; Нурлан `GET /tasks?project_id=2` → `[]` — задача в его проекте, но не видна ему.
**Что происходит:** (1) задача выпадает из всех досок владельца — фактически «тихое удаление» без права удаления; (2) владельцу утекает название чужого направления/проекта через `TaskOut.directions`; (3) ответ 404 при успешно применённой записи — фронт покажет ошибку, а данные уже изменены.
**Должно быть:** редактор не может снимать с задачи направления/проект, к которым сам имеет доступ только через шару, и не может перевести чужую задачу в контейнеры, недоступные владельцу задачи.
**Исправление:** в `_apply` при `access == EDIT` запрещать удаление направлений, через которые пользователь получил доступ (сравнивать `current` и `dir_ids`), и требовать, чтобы новые направление/проект были доступны *владельцу задачи* (`task_access(owner)` ≠ None) — либо проще: редактору разрешать менять `direction_ids/project_id` только в пределах контейнеров, где `owner_id == obj.owner_id`. Проверку доступа делать до `db.commit()` и при потере доступа откатывать (`db.rollback()` + 403).

### В2. Редактор создаёт задачу в направлении/проекте владельца, невидимую владельцу
**Файл:** `app/routers/tasks.py:31-38` (`_owner_for_new`), `app/scope.py:150-160` (`visible_tasks_query` не включает задачи в *моих* направлениях/проектах, только `owner_id`/шары/поручения).
**Воспроизведение:** Нурлан имеет `edit` на направление D Джека и владеет направлением N.
`POST /api/tasks {title: "Скрытая", direction_ids: [D, N]}` → 201, `owner: n.abilkhanov` (потому что «есть своё направление»). Джек: `GET /tasks?direction_id=D` → `[]`, `GET /tasks/{id}` → **404**. То же с `project_id: <проект Джека>, direction_ids: [N]` → задача в проекте Джека, `GET /tasks?project_id=<проект>` у Джека → `[]`.
**Что происходит:** на доске владельца существуют задачи, которых он не видит (статистика карты направлений, health-score, сводки — всё мимо). Нарушается правило PROJECT.md «задача, созданная редактором внутри чужого направления, принадлежит хозяину направления».
**Исправление:** в `_owner_for_new` определять владельца по контейнеру, а не по «любому своему направлению»: если задан `project` → `project.owner_id`; иначе если среди направлений есть чужие — владелец первого чужого (или запрет смешивать свои и чужие направления в одной задаче: 400). Дополнительно в `visible_tasks_query` добавить условие «задача лежит в моём направлении/проекте» (`exists task_directions ∧ Direction.owner_id == me` и `Task.project_id in (мои проекты)`), чтобы владелец контейнера всегда видел его содержимое.

### В3. `PUT /api/reminders/{id}` переносит напоминание на любую задачу; `fire_at` в прошлом принимается → мгновенный спам владельцу
**Файл:** `app/routers/simple.py:121-125`, `schemas.py:ReminderIn`.
**Воспроизведение:** Нурлан (edit на задаче A): `POST /reminders {task_id: A, ...}` → 201; `PUT /reminders/{id} {task_id: S(приватная Джека), fire_at: "2020-01-01T09:00:00Z", channels: ["telegram","email"], message: "спам Джеку", recipient: "owner"}` → **200**. Планировщик отправит на первом же тике (`fire_at <= now`).
**Что происходит:** те же причины, что в К1 (`task_id` не проверяется для нового значения); плюс отсутствие валидации даты.

### В4. Справочник «Люди»: любой пользователь правит и удаляет любого человека; удаление человека с поручениями → 500

### В5. Редактор направления переносит проект владельца в своё направление

## Средне

### С1. Удаление направления оставляет задачи-сироты и «висячие» шары; на sqlite повторное использование id даёт доступ к новой сущности
**Файл:** `app/routers/directions.py:34-40`, `app/models.py:Share` (нет FK на сущность, нет очистки).
**Воспроизведение:** направление D с проектом P (шары: D→Нурлан edit, P→Ева view), задачи в P и в D. `DELETE /directions/D` → 204. В БД: проект удалён; обе задачи живы с `project_id=None, directions=[]` (видны только в «Все задачи», без предупреждения, сколько задач останется); `shares` содержит `('direction',1)`, `('project',1)`; `GET /shares?entity_type=direction&entity_id=1` у Джека → 404 (отозвать нельзя). Затем `POST /directions` создаёт направление с **тем же id=1** (sqlite без AUTOINCREMENT) → Нурлан: `GET /directions` → `[(1, "Новое направление (Jack private)", "edit")]`.
На Postgres id из sequence не переиспользуются (кроме восстановления из дампа/`setval`), но мусорные строки остаются навсегда и попадают в `Grants` каждого запроса.
**Исправление:** в `delete` направления/проекта/задачи удалять `Share` по (`entity_type`, `entity_id`) в той же транзакции; в ответ на `DELETE /directions` (или отдельным `GET .../impact`) отдавать число затрагиваемых задач/проектов для подтверждения на фронте. Решить явно, что делать с задачами: оставить сиротами (тогда фронт должен показывать раздел «Без направления») либо запрещать удаление непустого направления (409).

### С2. Перенос проекта в другое направление: задачи получают новое направление, но сохраняют старое
**Файл:** `app/routers/projects.py:43-47`.
**Воспроизведение:** проект P в D1 с задачей T. `PUT /projects/P {direction_id: D2}` → `T.directions = [D1, D2]`; `GET /tasks?direction_id=D1` всё ещё содержит T.
**Что происходит:** задача числится в двух направлениях; статистика направления D1 продолжает считать чужой проект. Если это не осознанное решение (задачи кросс-направленческие), то нужно заменять `old_dir → new_dir`, если у задачи нет других причин быть в D1.
**Исправление:** при переносе удалять `obj.direction` из `t.directions` (если в старом направлении у задачи не было отдельной привязки, отличной от проекта) и добавлять новое; зафиксировать выбор в PROJECT.md.

### С3. Дублирующиеся `tool_ids` → 500 (IntegrityError на `tool_tasks`)
**Файл:** `app/scope.py:233-236` (`fetch_tools_for_task`), `app/routers/tasks.py:26`.
**Воспроизведение:** `POST /api/tasks {title, direction_ids: [], tool_ids: [1, 1]}` → **500**; `PUT /tasks/{id}` с тем же → 500. (Дубликаты в `direction_ids` sqlalchemy сворачивает — 201.)
**Исправление:** в `TaskIn`/`ToolIn` валидатор `list(dict.fromkeys(ids))` (дедупликация) для `direction_ids`, `tool_ids`, `task_ids`.

### С4. JWT без `sub` или с нечисловым `sub` → 500 вместо 401
**Файл:** `app/auth.py:51` (`int(data["sub"])`).
**Воспроизведение:** токен `{"email": "x", "exp": ...}` с валидной подписью → **500**; `{"sub": "abc"}` → **500**.
**Исправление:** `jwt.decode(..., options={"require": ["exp", "sub"]})` и обёртка `try: uid = int(data["sub"]) except (KeyError, ValueError): raise HTTPException(401)`.

### С5. Lost update: `PUT /tasks/{id}` без версии — автосохранение одного клиента затирает статус и чеклист другого
**Файл:** `app/routers/tasks.py:64-69`, `Task.updated_at` не используется для проверки.
**Воспроизведение:** оба клиента снимают снимок задачи. Клиент A: `PUT` с `status: in_progress, checklist[0].done: true` → 200. Клиент B (устаревший снимок): `PUT` с новым `description` → 200. Итог: `status=backlog`, `checklist[0].done=false`, `description` от B — изменения A потеряны без ошибки. Особенно вероятно при автосейве 0.6 с всей карточкой и одновременной работе редактора и владельца (или MCP `check_item` + открытая карточка).
**Исправление:** принимать в `TaskIn` необязательное `updated_at` (или `If-Unmodified-Since`/ETag) и возвращать 409, если оно отличается от текущего; на фронте при 409 перечитывать карточку. Как минимум сделать `PATCH`-семантику для чеклиста/статуса.

### С6. Пробелы во входной валидации (schemas.py)
**Файл:** `app/schemas.py` — `DirectionIn`, `ProjectIn`, `TaskIn`, `PersonIn`, `MindMapIn`, `ReminderIn`, `DelegationIn`, `ChecklistItem`.
**Подтверждено (все → 201):** направление/проект/задача/человек/майндмап с пустым или пробельным именем; `name` 5000 символов при `String(200)` и `title` 10000 при `String(300)`; `color` = `"javascript:alert(1)"` и `"#fff…"` длиной 101 при `String(16)`; `priority` 0, 99, −5 (модель обещает 1…5); `deadline` в прошлом; чеклист с дублирующимися `id`, с пустыми `id`/`text`; напоминание с `channels: []` и `fire_at` в прошлом; поручение создаётся сразу `status: done` с `check_at` в прошлом.
**Не проверено на Postgres:** превышение `String(N)` там даст `StringDataRightTruncation` → **500** (sqlite длину не проверяет). На Railway это именно Postgres.
**Исправление:** `Field(min_length=1, max_length=200)` + `str.strip()` через `field_validator` для имён/заголовков; `priority: int = Field(3, ge=1, le=5)`; `color: str | None = Field(None, pattern=r"^#[0-9a-fA-F]{6}$")`; `channels: list[Channel] = Field(min_length=1)`; уникальность `id` в чеклисте (валидатор); `fire_at`/`check_at` не в прошлом.

### С7. Мутация применяется, а ответ — 404 (см. В1)
**Файл:** `app/routers/tasks.py:69` (`db.commit(); return get_task_visible(...)`), аналогично `create` (`tasks.py:61`).
**Что происходит:** если в результате правки пользователь теряет доступ, запись уже зафиксирована, клиент получает 404 и считает, что ничего не произошло. Также `create` с чужим `project_id` + своими направлениями (В2) возвращает 201 — тут наоборот.
**Исправление:** вычислять доступ до коммита; при отсутствии — `db.rollback()` и 403 «после этой правки вы потеряете доступ к задаче».

## Низко

### Н1. Сравнение `X-API-Token` не константное по времени
`app/auth.py:56`: `token == settings.api_token`. Использовать `secrets.compare_digest(token, settings.api_token)`. Подтверждено чтением кода.

### Н2. Приглашение по адресу `"@cis.kz"` создаёт пользователя с пустым именем
`app/routers/shares.py:88-104`. `POST /shares {email: "@cis.kz"}` → **201**, `user: {name: "", email: "@cis.kz"}`. Добавить проверку локальной части (`EmailStr` из pydantic).

### Н3. `ms_oid == None` в callback превращается в `IS NULL`
`app/routers/auth.py:100`: `select(User).where((User.ms_oid == oid) | (User.email == email))`; при отсутствии `oid` в claims SQL становится `ms_oid IS NULL OR email = …` (подтверждено компиляцией запроса) — совпадёт с первым приглашённым, но ещё не входившим пользователем → вход в чужой аккаунт. **Не проверено** end-to-end: Entra всегда отдаёт `oid`, но защититься дёшево: `if oid: cond |= (User.ms_oid == oid)`.

### Н4. Удаление чужой/расшаренной сущности редактором отвечает 404, а не 403
`scope.get_owned` (`app/scope.py:183-187`). Нурлан (edit): `DELETE /directions/D` → 404, `DELETE /tasks/t` → 404. Семантически 403; фронт может показать «не найдено» и перезагрузить список. UX, не безопасность.

### Н5. Пользователь с `view` видит `tools.url`/`source_ref` задачи
`TaskOut.tools: list[ToolOut]` (`schemas.py`). Для будущих агентов `source_ref` может содержать идентификаторы таблиц/ботов — стоит отдавать тулы только `owner/edit`, как уже сделано для reminders.

### Н6. Любой пользователь может создать `Person` с e-mail другого пользователя — тот автоматически привязывается (`user_id`)
`simple.py:20-26`. Нурлан: `POST /people {name: "fake", email: "eve@cis.kz"}` → `user_id = <Ева>`. По замыслу (общий справочник), но имя записи задаёт не сама Ева; при её входе `callback` уже не создаст свою — стоит хотя бы брать имя из аккаунта при связывании.

### Н7. Мусорные `Share` после удаления задачи
`DELETE /tasks/{id}` (owner) удаляет напоминания/поручения/майндмапы (подтверждено), но `shares` с `entity_type='task'` остаются (см. С1).

- `view`: PUT/status/DELETE/reminder/project-create/share → 403/404; редактор не может делиться, удалять, отзывать и менять чужие шары (403); шара с собой — 400; `permission` вне `view|edit` — 400; `entity_type` вне списка — 400.
